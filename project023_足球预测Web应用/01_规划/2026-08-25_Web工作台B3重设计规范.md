# 足球预测 Web 工作台 B3 重设计规范

日期：2026-08-25
状态：设计已确认，待实施
适用项目：`project023_足球预测Web应用`

## 1. 目标与边界

将当前单页堆叠式工作台重构为“深色侧栏 + 明亮高密度内容区”的专业量化终端。功能、数据语义、事实源和后端接口保持不变；通过信息架构、组件拆分和渐进披露解决页面混乱问题。

成功标准：

- 日常用户进入首页即可看清今日销售日、已开售、已登记、待处理、证据完成度、版本和任务状态。
- 比赛列表支持快速扫描；点击一行后无需离开筛选上下文即可查看完整详情。
- 100元娱乐策略同时展示分配、保留余额、最大损失、选择依据和风险，不暗示正EV或生产推荐。
- 回测明确区分账面收益与统计有效性，未结算项不进入ROI。
- 采集、登记、LLM、结算和回测的进度、失败原因及重试入口集中可见。
- 桌面端优先；窄屏仍能完成查看、筛选和任务操作，非关键列按优先级收起。

不在本次范围：修改融合模型、推荐阈值、赔率来源、登记/结算口径、自动化计划任务、数据库结构或后端业务规则。

## 2. 信息架构与视觉系统

### 2.1 导航

左侧固定深色导航按职责分组：

- 每日工作：总览、比赛扫描器、100元娱乐策略。
- 评估分析：历史与回测、联赛表现、证据研究库。
- 系统管理：任务中心、版本治理、导出报告。

首页只保留今日总览、待办、比赛摘要、策略摘要和流程摘要；完整表格与统计进入专项页面。所有页面共享销售日选择器、最后刷新时间、服务状态和统一任务入口。

### 2.2 视觉规则

- 侧栏使用深墨绿色，金色仅用于品牌与少量关键提示；主内容使用浅灰背景和白色数据面板。
- 正常、警告、阻断分别使用绿色、琥珀色、红色，颜色必须同时配文字或图标，不能只靠颜色传达状态。
- 数字使用等宽或表格数字样式；主/平/客固定顺序和固定颜色，不因页面变化。
- 正文和表格保持高对比度；装饰效果从简，不使用霓虹、玻璃拟态、背景音乐或无意义动画。
- 所有时间明确日期、时区或销售日语义；百分比、赔率、金额和样本量不得省略单位。

## 3. 页面与交互

### 3.1 总览

- 顶部KPI：已开售、已登记、待处理、证据完成、当前模型版本。
- 待办条：未登记、证据缺口、临近开球和身份冲突，点击后带筛选进入比赛扫描器。
- 比赛摘要默认展示“需要关注”，可切换全部、未登记、证据缺口、已结算。
- 100元策略只展示预算、已分配、保留余额、项目数和“未验证正EV”标签。
- 流程摘要展示采集、量化登记、LLM证据、结算、回测的完成数和状态。

### 3.2 比赛扫描器

默认表格列：竞彩编号、比赛/联赛/开球、HAD赔率、量化主平客、模型模式、证据状态、登记状态。支持日期、联赛/时间排序、状态筛选和队名/编号搜索；窄屏优先保留比赛、概率和状态。

点击比赛打开右侧详情抽屉，保持当前滚动与筛选位置。抽屉按标签页展示：

- 概览：90分钟口径、HAD概率与赔率、模型模式、推荐门控、Top比分、大小球及核心风险。
- 全部盘口：HAD、HHAD、TTG、HAFU、CRS及各自`VALID/UNAVAILABLE/UNFITTED/NOT_OFFERED`状态。
- 证据：量化证据灯、近期状态、预计/官方首发、伤停、来源和采集时间；LLM方向、行动与理由单独展示。
- 审计：`match_id`、快照、`prediction_as_of`、模型版本、概率签名、数据来源和90分钟赛果。

缺失字段显示“暂无数据/未提供/未结算”及原因，不用0或空白伪装。

### 3.3 100元娱乐策略

- 固定展示预算上限、实际分配、保留余额和最大损失。
- 单关表展示玩法、比赛、选择、赔率、金额、市场共识概率、模型关系和证据风险。
- 组合卡展示腿数、不同比赛的每一腿、组合参考赔率、金额及任一腿失败的风险。
- 推荐依据分为市场筛选、模型关系、证据状态；明确同源一致不构成独立验证。
- 候选不足时保留余额；生产推荐、统计edge和Kelly状态持续显示为关闭或未验证。

### 3.4 历史与回测

- 顶部可切换娱乐策略、量化1X2、LLM轨、联赛和版本视图。
- 娱乐策略展示投入、返还、净收益、已结算/待结算、策略日数和累计收益曲线。
- 样本不足警告与收益数字同屏；短期盈利不得单独突出为策略有效。
- 逐项记录保留策略日、比赛、玩法、选择、赔率、金额、官方赛果、结算状态、返还和净收益。
- 量化与LLM回测继续分轨，展示各自样本分母，不合并概率或命中率。

### 3.5 证据、任务与版本

- 证据研究库按比赛展示近期状态、预计/官方首发、伤停、来源数、时间新鲜度、冲突和缺口；研究证据不回流生产概率。
- 任务中心统一承载采集、补登记、LLM、结算和回测。每个任务显示开始时间、进度、目标数、成功/失败数、当前消息和日志入口。
- 失败不得覆盖已成功结果；支持“仅重试失败项”。运行中禁用同类重复任务，并允许用户继续浏览。
- 版本治理默认只读，展示当前版本、概率签名、样本进度、在途样本和漂移状态。发布锁、版本接纳等高风险操作不进入普通快捷菜单。
- 导出报告保留现有入口，并展示生成时间、范围和下载状态。

## 4. 前端架构与接口

采用模块化原生前端，不引入React/Vue或新的构建链。FastAPI继续提供静态文件和现有JSON接口。

前端拆分原则：

- `index.html`只保留应用壳、导航和模块挂载点。
- 设计令牌、布局、组件和响应式规则拆为CSS文件；页面不再内嵌大段样式。
- API客户端、路由/状态、格式化工具、公共组件与各页面渲染器拆为ES模块。
- 单一应用状态保存销售日、当前页面、筛选器、选中比赛、任务轮询和缓存；页面切换不重复请求未失效数据。
- 继续复用现有`daily_strategy.js`和联赛命中率逻辑，但纳入统一组件与错误处理，完成后移除重复渲染代码。

现有接口保持兼容：`/api/board`、`/api/matches`、`/api/late-info`、`/api/daily-strategy`、`/api/daily-strategy/backtest`、`/api/history`、`/api/version-progress`、`/api/version-governance`、`/api/match/{match_id}`、任务POST接口、`/api/run/{run_id}`和导出接口。若页面需要组合数据，优先在前端组合现有响应；只有确认现有接口无法表达且不改变业务语义时，才新增只读聚合接口。

## 5. 状态、失败与可访问性

- 每个模块分别提供加载骨架、空状态、错误状态和重试按钮；一个接口失败不阻断其他页面。
- 请求显示来源接口和最后成功更新时间；刷新失败时保留旧数据并标记“可能过期”。
- 任务轮询在完成、失败、页面离开或网络错误时停止；恢复后允许手动重连。
- 所有用户可控文本在插入HTML前转义；动态属性不得直接拼接未经处理的值。
- 键盘可访问侧栏、筛选、表格行和抽屉；抽屉打开后管理焦点，`Esc`关闭并把焦点还给原行。
- 触控目标不小于约40px；窄屏使用折叠侧栏和全屏详情，不依赖横向拖动完成核心操作。

## 6. 验收与测试

- API契约测试：旧接口字段与语义不变，日期参数、空数据和错误响应仍可处理。
- 组件测试：概率格式、状态标签、证据灯、金额、策略单关/组合、回测记录和版本摘要。
- 交互测试：页面导航、日期与筛选联动、详情抽屉、任务启动/轮询/失败重试、导出和刷新失败保留旧数据。
- 回归测试：现有每日策略、联赛命中率、store view和LLM runner测试继续通过。
- 响应式测试：桌面宽屏、约1024px窗口和手机窄屏均无关键字段不可达。
- 内容审计：页面能找到现有工作台的全部功能；`market_only`、LLM投票、娱乐策略、生产门控和90分钟口径没有被重新解释。
- 人工验收：以真实销售日数据走完“刷新→筛选比赛→查看详情→执行任务→查看策略→结算回测→导出报告”的完整流程。

## 7. 发布与回滚

- 在现有项目内渐进替换静态前端，不迁移数据库和事实源。
- 首次发布保留旧页面副本作为短期只读回滚入口；新页面完成真实数据验收后再删除旧入口。
- 发布前运行前端静态检查、Python测试和本地浏览器冒烟；失败则继续使用旧页面。
- 不创建后台计划任务，不自动执行预测、结算或回测。
