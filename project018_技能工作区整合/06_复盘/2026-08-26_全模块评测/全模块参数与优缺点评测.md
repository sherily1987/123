## 1. 一句话结论

**工程治理是这套系统最强的部分，预测精度是最弱的部分。**

版本管理、失败关闭门禁、重放等价性审计、证据分级——这几块的严谨度已经超过多数业余量化项目。
但截至今天，**没有任何一份样本外证据表明模型概率优于同场市场**：全局 608 场配对
Brier 差 +0.0053（CI 跨 0），当前 m4 版本 48 场配对 Brier 差 +0.0032（CI 跨 0），
896 场无泄漏历史独立回放里 HAD/TTG/HAFU/CRS **四个市场全部劣于市场**。

系统当前的真实定位是：**一个校准良好的市场概率复述器 + 一套很硬的风控闸门**，
而不是一个有独立 alpha 的预测模型。这个定位本身没错，闸门也确实拦住了假 edge；
问题是几个月的优化大多花在了闸门上，独立信息通路几乎没有推进。

**⚠️ 重要前提（2026-08-26 复核）：这张表当前不生效。**
`recommendation_policy.py::_calibrated_primary()` 第一道判断是
`status not in ('VALID','APPROVED') → return None`，而 `recommendation_policy.json` 里写的是
`calibration_status: LEGACY_RESEARCH_ONLY`，因此该函数**每次都直接返回 None**。
而且即便启用，它产出的也是**推荐 confidence 值，不改 `final_1x2_pct`**——
不会影响任何已登记的概率或本报告 §3 的全部实测指标。
它是**一颗待引爆的地雷，不是正在渗漏的管道**。

**但这张表本身确实有问题，解禁生产前必须重做。** 映射**严重非单调**：模型给 0.50–0.55 时
校准到 69%，给 0.65–0.70 时反而校准到 40%，然后 0.70+ 又跳回 72%。真实的校准函数不会长这样。
单格 n 只有 45–117，这种形状**大概率是在拟合噪声而不是拟合偏差**。
表本身有 ECE 改善（0.0602→0.0438），但那是把样本内分箱命中率直接回填，
「分箱命中率当作该箱概率」这种做法必然让样本内 ECE 变好，**不构成样本外证据**。
风险在于：一旦有人把 `calibration_status` 改成 `VALID` 解禁推荐，这张表当天就开始生效。

## 4. 逐模块优缺点

### A. 核心引擎 `zu-yu-dashi-3`（31 文件 / 5,483 行）

**优点**

1. 每个衍生盘口**分别标注拟合状态**，不一概而论——这是罕见的诚实工程：
   `one_x_two: FITTED`、`ou_2_5/3_5: FITTED(Platt)`、`btts: VALIDATED_NO_CHANGE`、
   `asian_handicap: UNFITTED`、`hafu: PARTIALLY-CALIBRATED`、`advancement: FITTED-SMALL(n=24/31)`。
2. **BTTS 主动拒绝校准**：测过 Platt，测试集 ECE 0.02130→0.02650 反而恶化 24.4%，于是不施加。
   愿意接受「不改更好」的结论，绝大多数项目做不到这一点。
3. λ3=0.20 有真实的严格比赛日时间切分 OOS 依据（训练 949/测试 401），不是拍脑袋。
4. 崩溃场景已被包成结构化 `fusion_status=blocked`，不再抛裸 traceback。

**缺点**

1. **`RHO=-0.08` 全联赛硬编码**。挪超/瑞超/日职这些进球分布差异极大的联赛共用同一个低分修正。
   代码注释提到「rho 逐联赛拟合」是已知方向，但没做。
2. **默认去水法是 `proportional`**——理论上最差的一种（把水位按比例摊到所有选项，
   会系统性高估长赔）。`shin`/`power` 都已实现却不是默认，且没找到把它们纳入生产的评测结论。
3. **λ3 研究网格与生产值脱节**：`goal_model_ensemble.py` 只扫 (0.05, 0.1, 0.15)，
   重跑会选出 ≤0.15，与生产的 0.20 矛盾。这是一个会误导未来自己的坑。
4. `half_life=500` 单一固定值，没有按联赛赛程密度自适应。
5. 1.4.0 备注写明核心 `predict.py` 的两个崩溃**根因未修**，只是被外层包住了。

### B. 融合层 `football-quant-fusion`（100 文件 / 24,143 行）

**优点**

1. 失败关闭是真闸门不是摆设：`production_recommendations_enabled=false`，
   `market_only` 不得出胆、未校准 HHAD 不得出胆、市场依赖度 >80% 不得出胆。
2. 概率签名 / 决策策略签名 / 证据管线签名**三者分离**，改风控不会清空概率样本。
3. `job_ticket` 统一工单：全链路只认 `sporttery-<id>`，不靠数组顺序——多智能体交接的正确做法。
4. 影子路由（hybrid-shadow、intl_kelly、四市场）与生产严格隔离，`research_only=true`。

**缺点**

1. **100 个脚本、24k 行，但生产路径只用到其中很小一部分。** 目录里混着
   `input.json`、`input_0821_all.json`、`model_output_0822.json`、`before_fix_test_report.json`
   这类一次性运行产物，和正式模块平铺在同一层。新接手的人无法一眼分辨哪些是活代码。
2. **`market_weights` 的 5 个数没有拟合依据**。had 1.0 / hhad 0.9 / ou 0.8 / ttg 0.5 / hafu 0.35
   看起来是按「这个盘口我们多信任」手工排的序，没有对应的样本外验证。
3. **`edge_min_pp=5` 是一个永不触发的阈值**（实测最大 edge +1.6pp）。
   它写在配置里像个可调参数，实际语义是「永久禁用」。语义与实现不一致，容易误导。
4. **校准带表非单调**（见 §2.4），且是样本内分箱命中率回填。当前因
   `calibration_status=LEGACY_RESEARCH_ONLY` 而不生效，但解禁推荐的那一刻就会生效。
   建议在解禁前改成保序回归（isotonic）或 Platt，并强制单调。
   另注意它同时受 `edge_min_pp=5` 保护——两道门任一放开都会让它复活。

### C. 版本与发布治理 —— 全项目最强模块

**优点**

1. `model_version + probability_signature` 双主键 + 重放等价性审计，
   解决了「改一个字节就清空样本」的死锁。**这是真正原创且正确的设计。**
2. `probability_replay_check.py` 用旧样本的 `input` 重跑当前代码逐场比对——
   字节哈希答不了「概率变没变」，重放能答。m1 已实测 35/35 一致，m4 已 59/59 一致。
3. 别名必须 `(model_version, signature)` 精确成对，等价结论不外推到未重放路由——边界写死了。
4. 同一把尺子既**肯定**过 m1（35/35 通过，34 场免于重攒），也**否决**过 1466 场 legacy。
   方法论一致，不因结论方向而放松。
5. `release_lock.py` 发布窗口锁定，`audit_version_consistency.py` 抓「改概率忘 bump」。

**缺点**

1. **版本碎片化已经很严重**：609 场已结算样本里，m1 33 + m2 1 + m3 53 + m4 48 + 无法归属 474。
   **只有 7.9% 的历史样本能为当前版本作证。** 治理越严，可用分母越小。
2. **当前正在发生签名漂移**：14 条 08-25 的记录签名是 `42d3ccacb1d9`，与发布锁的
   `48d50abee08c` 不符，**被静默排除出 current cohort**。说明发布锁与实际预测运行之间
   仍有缝——锁住了发布窗口，但那批预测跑的不是锁里那份代码。
3. m4 自身也分裂成三个签名（`42d3ccacb1d9`×14 / `48d50abee08c`×11 / `5c34721daa91`×37），
   靠别名手工缝合。这条路走下去，每次微调都要跑一次重放才能不丢样本，成本在累积。
4. 门槛设计的现实性问题：联赛级 `minimum_n=300`，当前最多的意甲只有 9 场。
   按目前每天约 10 场的积累速度，**单个联赛达标要 30 年**。这个门槛实际上不可达。

### D. 证据管线

**优点**

1. 两级门控定义清楚：研究预测门 vs 购买推荐门。「搜索到网页」明确不算验证通过，
   必须留 URL、采集时间、身份核验结果。
2. 媒体预测首发有独立标签（「预计首发（媒体预测，非官方确认）」），不与官方确认混淆。
3. 跨验证要求 ≥2 个不同发布方，同一发布方的多个域名只算一次。
4. 08-24 那 11 场的实测结果被如实记录：研究门 11/11 通过，**购买门 0/11 通过**，
   没有因为「交叉搜索做完了」就放行。

**缺点**

1. **抓取成功率低**：Scrapling/BB-browser 11 场只成功 4 场（36%）。
2. **首发确认率为 0**：0/11 双方首发确认，停赛仅 2/11 确认，9 场停赛字段仍是
   `EMPTY_UNCONFIRMED`。购买门实际上从未被打开过。
3. **证据分层在回测里完全没起作用**：`evidence_stratification` 里
   `evidence_age:unknown` 和 `evidence_gap:no_gap` 两个分层的 n 都是 609（=全量），
   说明**所有历史样本的证据年龄都是 unknown**，分层等于没分。想用证据质量解释精度差异，
   现在没有数据支撑。
4. 旧档案不可信：审计发现有记录摘要没引用任何 E 编号，但 `reasoning_ok=true`。

### E. LLM 对比轨（48 文件 / 12,912 行，222 测试全过）

**优点**

1. **EV 计算的修复是本项目最有价值的一次纠错**：删掉 `votes_to_probabilities()`
   （把投票计数当概率），改为无校准概率来源时 `fail closed`，
   `skip` 时**刻意不含 `ev` 键**——下游误用会 KeyError 而不是拿到假数字。
   实测单场虚高量级：平局 EV 从 +88.6% 修正到 -0.7%，**89 个百分点**。
2. 概率来源已接上量化轨的 `final_1x2_pct`（真实校准概率），且**明确禁止回退到投票比例**。
3. 接上之后**仍然不出胆，而且这是对的**：`calibration_status != VALID` 不出胆、
   `market_derived=True` 不出胆——对同一个盘口算 EV 量到的是庄家水位不是独立 edge。
   这个判断与融合层 `edge_min_pp=5` 独立得出同样结论，互为佐证。
4. 双轨纪律清晰：借用轨道A概率只发生在 EV 这一层，方向/比分/投票/登记各自独立。

**缺点**

1. **几乎没有可评测的样本**。K3 校准样本：153 个工单扫出 **1 条**已结算，且方向预测错误
   （预测平，实际 3-0 主胜）。DeepSeek V4 Flash：10 条 LLM 记录，**0 条**合格已结算
   （9 条待官方赛果、1 条非目标模型）。**LLM 轨目前没有任何统计意义上的成绩单。**
2. **`strength` 是投票比例不是概率**，这个陷阱已经导致过一次真实翻车（报告里把 `skip`
   场次当推荐抄进表格）。字段名仍叫 `strength`，语义地雷还在。
3. **目录卫生很差**：模块根目录混着 100+ 个 `.html` / `.json` 一次性抓取快照
   （`bbc_match.html`、`wiki_spl_2026.html`、`fotmob_neom.html` 等）与正式源码平铺。
   虽然被 `.gitignore` 排除，但阅读体验极差。
4. C 盘旧目录 `C:\Users\Administrator\football-llm-predictor\` **仍未删除**，
   是一份过期快照。历史上分裂过一次并造成过错误结论，风险仍在。

### F. 数据接入与联赛训练（007 + 021，147 测试全过）

**优点**

1. **覆盖面是真的广**：55 个联赛的 xG 计划，47 个正常纳入 / 8 个标记 `forced_low_share`。
   三源接入（apifootball.com / api-sports.io / football-data.co.uk）。
2. **代理 xG 系数有守恒自检**：inside_outside 系数 24147 场 / 26 联赛，
   总量偏差 -0.046%，`total_conserved: true`，`primary_gt_secondary: true`。
3. **低质量联赛不藏着**：`forced_low_share` 场次直接写明「可用场次仅占完赛 58.3%，
   低于 60%，强度由少数比赛拟合，置信度低于其余联赛」。
4. **抓到过两个真实的数据毒**：(a) football-data.co.uk 的 `KOR.csv` 实际重定向到
   `NOR.csv`（韩职拿到挪超数据），已隔离到 quarantine；(b) 淘汰赛制比赛因只认
   `Finished`/`FT` 被整场丢弃，且比分是点球战后而非 90 分钟——修复后找回世界杯决赛、
   欧冠 21 场 + 欧联 27 场点球大战。**这两个 bug 不修，所有杯赛结论都是错的。**
5. 2026-08-13 起立规矩：无 xG 数据源的新联赛不再追加豁免，只保留已验证的 5 个。

**缺点**

1. **`train_until: 2025-08-08`**，而今天是 2026-08-26。代理 xG 系数的训练截止在一年前。
   如果是刻意留 2025-26 整赛季做 OOS，那是好设计但应写明；如果是忘了重拟合，
   那就是一整季的数据没进模型。**这一点报告里没写清楚，需要确认。**
2. **8 个联赛是「强行纳入」**（芬超/乌超/塞浦路斯甲/保加利亚甲/韩职等），
   它们的强度参数由不到 60% 的比赛拟合，置信度自己都承认低。
3. 黑山甲/波黑甲**至今未跑赢频率基线**——即模型不如「按历史频率瞎猜」。
4. 世界杯标 `not_trained`（4 年一届，滚动重拟合方法论不适用）——这是诚实的，但意味着
   大赛期间这套系统没有能力。
5. `lifecycle` 从 `candidate` 改成 `production` 只表示「已训练」，不代表质量达标——
   标签语义与直觉相反，容易被下游误读。

### H. 决策 / 策略层

**优点**

1. **娱乐预算策略与生产购买推荐彻底分离**，这是这个模块最正确的设计。
   `RECREATIONAL_SINGLE_STAKES` = HAD 14 / TTG 10 / HAFU 8 / CRS 6 元，
   串关 2 串 16 元、3 串 8 元，每条都带 `maximum_loss_amount`，
   `purchase_basis` 明确写 `recreational_budget`，不冒充正 EV。
2. `build_combinations()` 明确不做仓位（`stake_sizing_status: NOT_RELEASED`）——
   凯利仓位没有被偷偷放出来。
3. 各市场有独立的概率/赔率/水位上下限（如 HAD 要求概率≥42%、赔率 1.30–2.8、
   水位≤16%；CRS 概率≥8%、赔率 4–15、水位≤50%）。

**缺点**

1. **这些限值全是先验拍的，没有一条有回测依据。**「HAD 最低概率 42%」「CRS 水位上限 50%」
   这些数字看不到任何拟合或敏感性分析来源。
2. 娱乐策略允许在首发未确认时下 HAD/TTG——与证据门的严格程度不一致（虽然是刻意放宽，
   但两套标准并存容易被误读为「证据门通过了」）。
3. 配额 HAD 3 / TTG 2 / HAFU 1 / CRS 1 同样是先验。

## 6. 建议优先级

**如果只做三件事：**

1. **修那 11 个过期日期测试**（半小时的活）。当前证据管线这条线没有测试保护，
   而它恰好是正在改的分支（`feat/evidence-source-reachability`）的主题。

2. **查签名漂移**（见下方 P0-4 说明）。这条每天都在丢样本，而 current cohort 才 48 场。

   （原本排在这里的「重做校准带表」已降级：复核确认它当前因
   `calibration_status=LEGACY_RESEARCH_ONLY` 而不生效，改成解禁生产**之前**的必办项即可。）

3. **停止在 `market_only` 上堆样本，集中攒 hybrid。**
   §3.4 和 §3.5 已经把话说死了：市场复述通路的 ECE 0.0226 是同义反复不是本事，
   而 896 场无泄漏回放证明当前独立通路四个市场全输。
   靶子只有一个——**让独立 λ 通路（球队强度 + 代理 xG）真的能打赢盘口**，
   在此之前调校准层、调权重、调门槛，都是在调错地方。

**关于 P0-4（签名漂移）**：14 条 08-25 记录用的不是发布锁里那份代码。
建议查一下是发布锁没更新还是预测跑的是旧进程——这条如果不查清，
后续每天都会有样本被静默丢出 current cohort。
