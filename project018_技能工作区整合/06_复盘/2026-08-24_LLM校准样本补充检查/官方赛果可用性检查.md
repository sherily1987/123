# LLM 校准样本补充检查

日期：2026-08-24  
目的：确认共享工单中 DeepSeek V4 Flash 校准样本是否已有可进入研究分母的官方 90 分钟赛果。

## 检查命令

```powershell
python project018_技能工作区整合/02_脚本/skill/football-quant-fusion/scripts/fusion_cli.py settle --date 2026-08-24 --dry-run
```

这是只读检查，不写入结算库、不改变预测登记，也不改变模型版本。

## 结果

| 项目 | 数量 | 解释 |
|---|---:|---|
| 待结算工单 | 10 | 当前日期筛选后仍在途的场次 |
| 可按固定比赛 ID 匹配到赛果候选 | 5 | 仅表示本地/接口返回了候选比分 |
| 尚无赛果 | 5 | 仍不能评分 |
| `official_finished` | 0 | 没有一场通过官方完成状态门禁 |
| 本次实际结算 | 0 | dry-run，不写入 |

可匹配候选包括 `sporttery-2041018` 至 `2041023` 中的五场（不含 `2041024`、`2041025`、`2041026`、`2041027`）。这些比分在官方状态变为 `finished` 且 `score_90_status=verified` 前，不得进入 LLM 校准分母。

## 对 DeepSeek 校准的影响

当前 DeepSeek V4 Flash 校准样本仍为：

- `jobs_scanned=153`
- `llm_rows=10`
- `eligible_settled_rows=0`
- `calibration_gate=INSUFFICIENT_SAMPLE`

因此不能据此计算 Brier、LogLoss、ECE，也不能把候选赛果直接补成标签。后续应先运行正式结算流程并复核每个 `match_id`、90 分钟比分、来源和时间戳，再重新生成校准样本。

## 安全边界

Sporttery 官方赛果仍是生产结算基准；APIFootball 或其他来源只能在显式启用的回退路径中使用，并且必须满足 `score_90_status=verified`。本检查没有启用回退，也没有修改生产推荐门禁。

## Scrapling 现场解析回归

对一篇跨联赛的 Sports Mole 赛前页面做了真实抓取验证：

- HTTP：`200`
- 页面：Bologna vs Lazio 赛前预览
- 修复覆盖：Setext 标题、粗体 `possible starting lineup` 标签、纯 W/D/L 近期状态、`Team News` 下的 fitness doubt
- 修复后字段状态：`recent_form=VALID`、`injury=VALID`、`starting_xi=PREDICTED`
- 仍保持缺口：`team_stats=UNAVAILABLE`、`suspensions=UNAVAILABLE`

原始 Scrapling Markdown 快照：`sportsmole_probe.md`。预计首发仍标为 `PREDICTED`，没有被提升为官方首发；没有明确停赛段落时也不会推断“无人停赛”。

通过生产采集入口 `collect_one` 的端到端结果：

```json
{
  "provider": "sportsmole_scrapling",
  "research_only": true,
  "scrapling_attempts": [{"status": "ok"}],
```

这证明通用来源不是只被“发现”或只写入链接，而是能在 API/FotMob 不参与时直接形成带来源 URL、采集时间和缺口状态的证据快照。
