# m2 窗口固本：版本别名、路径残留与 LLM 轨 EV 方法论

接手时 `model_version=m2`（发布锁 2026-08-15T15:33Z）。方向定为**不动概率文件**、
保住 m2 发布窗口，做三件事：窗口内固本、LLM 轨 EV 方法论修复、让 m2 真实累积样本。
模型精度攻坚（需 bump m3、窗口作废重开）本轮明确不做。

## 一、接手时的真实状态与三处过时结论

`AGENTS.md` 有三处结论已被实测推翻，会误导下一个接手的 agent，已就地更正：

| --- | --- |

| 数据分裂未修 | daily-pipeline 已修；**但其余脚本没修**，见第三节 |

回测基线（474 场，全部 legacy）：Brier 0.6166；同场配对 bootstrap
`模型-市场 = +0.0082`，95%CI `[-0.0035, +0.0210]` 跨 0——**模型统计上不优于市场，
点估计略差**。这是精度攻坚的靶子，本轮未打。

## 二、核心发现：m1→m2 的 bump 是数值中性的

08-15 13:32 UTC 登记的 34 场（08-16 赛事）签 m1，两小时后 bump 到 m2，m2 从 0 起算。

用同一批 input 重放当前代码：**35/35 场 `final_1x2_pct` 与 `model_1x2_pct` 完全一致**
（证据：`审计_m1概率等价性重放_20260816.json`）。那次 bump 由影子路由重构与签名字段
拆分的**字节变更**触发，生产 market_only 路由的概率一位没动。

### 根因

`probability_signature` 仍然是概率文件的**字节哈希**。
`40_模型/模型版本管理_打破current死锁.md` §1.3 诊断的「字节哈希无法区分影响概率的变更
与不影响概率的变更」，在缩小后的 `probability_files` 名单里原封不动地成立——死锁没有
解除，只是范围变小了。方案上线第二天就被自己踩中。

### 补丁

1. `scripts/probability_replay_check.py`：取旧样本登记时保存的 `input` 重跑当前代码，
   逐场比对概率，判 `equivalent` / `changed` / `inconclusive`。
2. `config/version_manifest.json` 新增 `model_version_aliases`：只有判 `equivalent`
   的旧版本可写入，条目必须带签名、验证时间、验证命令、验证覆盖的路由和证据说明。
3. `fusion_backtest.version_cohort()`：`(model_version, probability_signature)` 与别名
   条目**精确成对**匹配时也算 `current`。

这与 08-15 用重放测试**否决** 1466 场 legacy 并入是同一套方法论（那次 30 场抽样 11 场
概率不同）。判否就重攒，判是就并入，标准不随结论方向改变。

**边界**：等价结论只覆盖被重放的 `market_only` 路由，不可外推到 hybrid 或未重放的
衍生市场；别名不改写样本原始 `model_version`，分版本明细里 m1 仍显示 m1。

**效果**：m2 在途样本 0 → 34。注意回测只数已结算样本，`current_version_n` 要等
08-16 赛事结算后才会脱 0。

## 三、路径残留：`--store` 默认值仍指外部套件

`assert_writable_target()` 只在 `fusion_daily_pipeline.py` 里被调用，**不是全局守卫**。
复查发现这几处默认值仍硬编码指向外部 `football-quant-fusion-suite`：

- `fusion_backtest.py`（读）、`sample_audit.py`（读）、`evaluate_walk_forward.py`（读）、
  `fusion_combo.py`（读）——忘了传 `--store` 就**静默评测错的库**，
  `calibration_gate` / `current_version_n` 会跟着一起错；
- `odds_api_adapter.py`（**写**）——国际盘数据 append 进只读引用副本，仓库内看不到。

已全部改走 `runtime_paths`。显式传 `--store` 指向外部仍能绕开，这是设计上的口子，不是 bug。

以 `sys.path.insert` 引用外部套件 zu-yu-dashi-3 的一次性研究脚本
（`calibrate_league_kt.py`、`refit_kt_power.py`、`understat_enrich.py` 等）本轮未动。

## 四、新增可观测性：`version-progress`

原先「当前版本还差多少样本」只能手写 python 查，且回测只给已结算数、不给在途数。
新增 `fusion_cli.py version-progress`，同时给已结算、在途未结算、距 100/200 的距离，
以及 `signature_drift`（改了概率文件却没 bump 版本的样本，会被静默排除出 current）。

口径说明：它的 settled 是回测 `n` 的上界（回测会丢弃已结算但无法评分的记录；
2026-08-16 实测两边都是 474，当前没有这类记录，但不保证永远相等）。
**门禁分子仍以回测 `calibration_gate` 为准。**

## 五、LLM 轨 EV 方法论修复

`ev_calculator.py` 把 LLM 投票计数归一化后直接当概率代入 `EV = 概率×赔率 - 1`。
3 个模型投票时票比只能取 0、1/3、2/3、1；3:0 一致时票比 = 1.0，EV 直接变成「赔率 − 1」，
任何冷门都会算出巨额正 EV。票比衡量的是模型间一致程度，不是事件发生概率，且从未校准。

已改为 fail closed：

- `votes_to_probabilities()` 删除，调用抛 `NotImplementedError`；票比走
  `votes_to_vote_share()`，语义写死在函数名里；
- `generate_betting_recommendation()` 必须同时收到 `calibrated_probs` 与 `prob_source`
  才产出 EV，否则 `action=skip`，只给 `vote_share_analysis`——**刻意不含 `ev` 键**，
  下游误用会 KeyError 而不是拿到一个看起来合理的假数字；
- `predict.py` 决策层同步收紧：只有 `action=bet` 的 `ev_analysis` 才传给
  `decide_single_pick()`。此前无论 skip 与否都传，等于在代码里绕开自己的风控闸门——
  与 08-15 报告手工摘录时犯的是同一个错，只是那次发生在人工环节；
- 顺带删掉 `find_positive_ev_bets()` 里签名上有、函数体里从没用过的
  `max_strength_threshold`（调用方以为设了强度门槛，其实没生效）。

**代价**：当前每场都是 `action=skip` + 票比展示，EV 排序暂时消失。要恢复必须接一个真实
概率来源（如轨道A的 `final_1x2_pct`）并在 `prob_source` 写明——这一步本轮未做，
因为它触及双轨「各自登记、各自结算、不合并」的纪律边界，需要单独决策。

**两侧同步**：生产 `C:\Users\Administrator\football-llm-predictor\` 与仓库副本
都已更新 `ev_calculator.py` + `test_ev_calculator.py`（备份
`ev_calculator.py.bak_20260815_pre_ev_fix`）。顺带量化了两侧分裂程度：生产 `predict.py`
1101 行、仓库副本 800 行，**仓库副本是停更旧分支，不能拿它推断生产行为**。

## 六、一个被否决的做法

曾考虑把 08-16 那 34 场重新快照成 m2 来补样本。**否决**：那会把 m2 的开局样本全部换成
贴近开球的晚快照（赔率更成熟、阵容已明），而历史样本是正常开售日的早快照。这批样本恰恰
要用于决定能否解禁生产推荐的 OOS 评审，等于给评审埋一个自己造的偏差。
改用重放别名解决——它不制造任何新样本，只是纠正既有样本的归属。
