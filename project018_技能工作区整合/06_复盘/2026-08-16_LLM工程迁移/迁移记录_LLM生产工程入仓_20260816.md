## 背景

`AGENTS.md` 长期把这条列为**头号警告**：LLM 轨真正在跑的代码不在 git 仓库里，而在
`C:\Users\Administrator\football-llm-predictor\`（非 Git）；仓库里

### 但真实预测跑不完，两个**与迁移无关**的既有问题

**问题一：apifootball.com 的 key 根本没配，且两处代码拿另一家供应商的 key 兜底。**

`mcp_query.py` 读 `MCP_APIFOOTBALL_API_KEY`（未设置），空 key 导致
`Malformed Authorization header` → 拿不到 `Mcp-Session-Id` → `No valid session ID provided`。

排查中一度以为 `API_FOOTBALL_KEY` 可以兜底并改了代码，**结果证明是错的**：
`API_FOOTBALL_KEY` 是 **api-sports.io** 的 key，与 apifootball.com 是两家不同供应商
（AGENTS.md project021 条目早已写明）。加上回退后错误从「header 格式错」变成
「Authentification failed!」，**更难定位**。已改回正确语义并加显式报错：

- `project001_足球预测/02_脚本/mcp_query.py`：只读 `MCP_APIFOOTBALL_API_KEY`，
  新增 `require_key()`，空 key 立刻抛错并点明「API_FOOTBALL_KEY 是另一家的，不能替代」；
- `mcp_evidence.py::_api_football_key()`：原本**优先**取 `API_FOOTBALL_KEY` 去请求
  `apiv3.apifootball.com`，同一个跨供应商错误，已改为只认 `MCP_APIFOOTBALL_API_KEY`。

跨供应商回退比没有回退更糟——它把「没配 key」伪装成「key 无效」。

**待用户处理**：配置 apifootball.com 的 key 后证据富集链路才能跑
（`setx MCP_APIFOOTBALL_API_KEY "<apifootball.com 的 key>"`，需新开终端生效）。

**问题二：证据措辞与目录关键词表脱节，导致整场被拒且理由误导。**

08-17 的三场预测全部返回 `evidence_audit_failed / audit_unavailable_status_mismatch`。

各日期证据目录状态分布对比：

| 日期 | 证据文件 | 目录条目 | UNAVAILABLE |
| --- | --- | --- | --- |
| 08-14 | 14 | 527 | 3 |
| 08-15 | 48 | 963 | 1 |
| **08-17** | **7** | **49（每场 7 条）** | **0** |

08-17 证据是骨架级的，只有体彩自带的赔率/开球/队名，富集步骤没跑成（即问题一）。
而这 7 条里的 `E1「体彩官方接口无伤病/大名单字段，赛前官方首发与伤员名单尚未公布」`
语义上就是不可得，但 `build_evidence_catalog()` 的关键词表
（`无记录/0条/未获得/未检索到/未拿到/证据缺口`）不覆盖这种措辞 → 标成 `SINGLE_SOURCE`；
审计模型如实把它归入 `unusable_evidence_ids` → 状态对不上 → 整场拒绝。

**未修**：这是门禁按设计 fail closed，改关键词表等于放宽 LLM 轨的证据门槛，
是策略决定不是 bug 修复，需单独决策。但至少要知道：**当前这个失败理由是误导性的**，
真正的原因是证据太薄，不是审计模型乱答。

### key 配置后的续验（2026-08-16 当日）

用户配好 `MCP_APIFOOTBALL_API_KEY` 后继续验证，又挖出两个既有 bug，均已修：

**问题三：MCP 结果被服务端截断，客户端不看 `truncated` 字段。**

`get_football_matches` 单次默认只返回 50 条，超出时在响应里给
`truncated: true` + `note: "120 matches matched ... only the first 50 are shown"`。
原实现直接取 `matches` 就用，**失败表现是漏场次而不是报错**——西甲那场排在 50 名之后，
被判「未匹配到 apifootball 比赛, 跳过」。

修复（`fetch_match_candidates()`）：显式传 `limit=100`（schema 上限，默认才 50）+ 按天分次拉
再按 match_id 去重合并；仍被截断时明确警告。实测候选 50 → **120（完整）**，警告消失。

**问题四：证据文件名的净化正则是纯 ASCII，中文队名整段丢失且会静默覆盖。**

`re.sub(r'[^a-z0-9]+', '_', name.lower())` 把中文折成一个下划线，
「西班牙人 vs 莱万特」生成出 `evidence_001_____mcp.md`。人工 `--match-id` 路径下
`home_en`/`away_en` 拿到的就是 raw 里的中文名，必然踩中。
**后果不只是难看：同一天两场比赛会折成同一个文件名、静默互相覆盖。**
已改用 Unicode 感知的 `\w`（新增 `_safe_name()`），验证生成
`evidence_001_西班牙人_莱万特_mcp.md`。

**MCP 证据链路已确认可用**：lineups / odds(13条) / predictions / h2h 四路都正常返回并写出证据块。

### 仍未跑通完整真实预测，剩余两道坎（都是既有的）

1. **`TEAM_NAME_ALIASES` 只有 6 条**（联赛表却有 32 条），全是北欧/葡超零散球队。
   主流联赛的中文名→英文名自动匹配基本不成立，代码按设计「未知别名时安全拒绝」，
   要求走 `--match-id` 人工核验。**没有补别名表**——猜错别名会把证据挂到错误的比赛上，
   正是这段代码刻意防的风险，属数据策展任务。
2. **`predict.py` 需要的是主证据文件** `evidence_NNN_主队_客队.md`（来自网页检索/Crawl4AI
   采集），`_mcp.md` 只是附加数据块。08-15 那 48 个主证据是完整采集跑出来的；
   本轮只验证到 MCP 数据块这一层。
